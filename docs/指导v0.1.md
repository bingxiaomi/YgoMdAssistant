# Yu-Gi-Oh! Master Duel 实时战术分析助手
## 项目总体技术设计文档 v0.1

- 项目代号：YGO Tactical Assistant
- 文档版本：0.1
- 开发平台：Windows 10/11 x64
- 首选语言：Python + C++
- 项目类型：实时视觉分析、游戏规则推演、本地 AI 战术助手
- 核心目标：从游戏画面还原对局状态，分析当前局面，推荐下一步操作，并在对手打断后重新规划 Combo。
- 设计原则：模块化、事件驱动、规则验证优先、离线与实时共用一套数据管线。

---

# 1. 项目目标与范围

## 1.1 最终目标

构建一个面向《游戏王 Master Duel》的战术分析系统，能够读取游戏画面，识别卡牌和决斗事件，重建当前对局状态，并利用游戏王专项本地模型与规则搜索引擎提供实时决策建议。

系统不仅需要理解卡牌文本，还需要能够追踪卡牌资源、发动次数、召唤限制、连锁结算和当前展开路线。

最终需要实现以下能力：

1. 实时读取 Master Duel 游戏窗口。
2. 识别决斗日志、当前效果描述、卡片详情、阶段和场面变化。
3. 将连续画面转化为结构化事件流。
4. 重建当前对局状态，包括已知信息、未知信息和状态置信度。
5. 识别当前 Combo 进度，预测下一步操作。
6. 使用规则引擎和搜索算法生成合法的展开路线。
7. 对当前路线进行风险分析，识别可能被打断的位置。
8. 当效果被无效、资源发生变化或原路线失效时，重新规划剩余路线。
9. 通过本地模型解释推荐原因，并比较不同路线的收益与风险。
10. 支持录制回放分析、数据导出、模型训练与后续评测。

## 1.2 第一阶段不做什么

为控制项目复杂度，第一阶段不实现：

- 从零训练视觉大模型。
- 从零实现完整的游戏王规则引擎。
- 直接从 Master Duel 进程内存读取状态。
- 自动代替玩家执行对局操作。
- 在信息不完整时强行推断对手全部手牌。
- 将未经验证的 Combo 搜索结果直接认定为最优策略。
- 一开始就支持全部卡组、全部卡池和所有复杂规则。

第一阶段优先打通视觉识别、对局事件重建和数据导出。Combo 搜索与本地模型可以先通过统一接口接入，再逐步增强。

# 2. 总体系统架构

系统采用分层架构，将视觉感知、状态管理、规则验证和 AI 决策分离。

```text
                    Master Duel
                         |
              +----------+----------+
              |                     |
         实时窗口采集           录像文件输入
              |                     |
              +----------+----------+
                         |
                  Frame Pipeline
                         |
             +-----------+------------+
             |           |            |
         决斗日志 OCR  当前效果识别   场面识别
             |           |            |
             +-----------+------------+
                         |
                 Event Fusion
                         |
                 Duel Event Stream
                         |
                State Reconstruction
                         |
              +----------+-----------+
              |                      |
         Card Knowledge         Duel State
          卡牌知识库              当前局面
              |                      |
              +----------+-----------+
                         |
                Decision Coordinator
                         |
          +--------------+--------------+
          |              |              |
      Rule Engine    Combo Search    Local LLM
      合法性校验       路线搜索        策略分析
          |              |              |
          +--------------+--------------+
                         |
                   Route Evaluator
                         |
                 Tactical Advisor
                         |
          +--------------+--------------+
          |              |              |
       实时建议       多路线对比       风险提示
                         |
                 UI / Data Export
```

## 2.1 三类输入

### A. 实时画面

通过 Windows 窗口采集获取当前游戏画面，持续更新视觉状态。

### B. 离线录像

导入 MP4 等录像文件，使用与实时模式相同的帧处理和事件解析管线。

离线模式支持暂停、逐帧回看、调整时间点和人工修正识别结果。

### C. 可选的结构化数据

后续允许导入卡组、已验证的回放数据和其他合法获取的对局记录。

原始 Master Duel 回放与 EDOPro/ocgcore 回放格式不能默认视为兼容，必须通过独立适配器处理。

## 2.2 两种运行模式

**Replay Analysis：** 离线复盘、日志导出、Combo 数据生产和模型评测。

**Live Advisor：** 实时画面分析、局面跟踪、下一步推荐和中断后重新规划。

两种模式必须共享 Frame Pipeline、事件模型、状态模型和卡牌知识库，不允许分别维护两套互不兼容的解析逻辑。

# 5. 实时画面采集与视觉识别

## 5.1 采集接口

定义统一的帧对象：

```python
@dataclass
class Frame:
    frame_id: int
    timestamp_ms: int
    image: np.ndarray
    source: str
    width: int
    height: int
```

`source` 可以是 `live_window` 或 `video_file`。

所有下游模块只接收 `Frame`，不需要知道帧来自实时窗口还是录像文件。

## 5.2 采集策略

初始配置建议：

- 实时采集目标：30 FPS。
- 视觉变化检测：按需要处理，不要求每帧都进行完整识别。
- OCR：只处理发生变化的文字区域。
- 卡图匹配：只在卡片进入新区域、身份不确定或需要重新确认时运行。
- UI 更新：控制更新频率，避免因渲染影响采集。

30 FPS 是采集目标，不是 OCR 或模型推理频率。

必须使用有界队列。处理速度落后时，允许跳过中间帧，但不能让队列无限增长，导致实时建议越来越滞后。

## 5.3 区域识别

第一版使用可配置 ROI，不把截图坐标硬编码在业务逻辑里。

需要支持：

1. 根据游戏窗口位置和尺寸定位区域。
2. 按相对比例缩放区域。
3. 手动拖动调整识别框。
4. 保存不同分辨率的布局配置。
5. 实时预览 ROI 和 OCR 结果。

初始 ROI：

| ROI | 内容 | 优先级 |
|---|---|---|
| R1 | 右侧决斗日志 | P0 |
| R2 | 右上角当前效果描述 | P0 |
| R3 | 左侧卡片详情 | P0 |
| R4 | 阶段、回合和 LP | P1 |
| R5 | 双方手牌 | P1 |
| R6 | 场地怪兽区、魔陷区 | P1 |
| R7 | 墓地、除外和额外卡组信息 | P2 |

必须先支持手动校准，再考虑自动寻找界面元素。不同窗口大小、UI 缩放和游戏动画可能使固定坐标失效。

## 5.4 图像识别策略

卡牌识别使用多证据融合：

1. OCR 读取可见卡名。
2. 使用卡名别名表处理语言差异和 OCR 错字。
3. 利用卡图特征匹配候选卡牌。
4. 根据前一帧的卡牌身份和位置历史进行校正。
5. 根据当前决斗日志和可见卡组信息缩小候选范围。
6. 不确定时保留多个候选，不强行输出唯一结果。

禁止将“当前被鼠标选中的卡片”自动等同于“刚刚发动的卡片”。需要结合日志、效果描述和时间顺序确认事件归属。

# 6. 决斗日志、效果描述与事件融合

## 6.1 三类核心信息源

### A. 决斗日志

主要提供：

- 发动与处理顺序。
- 阶段和连锁信息。
- 卡牌名称。
- 公开的卡牌移动或效果结果。
- 部分效果选择信息。

### B. 当前效果描述框

主要提供：

- 当前发动的效果。
- 同一卡片不同效果之间的区分。
- 多选一效果的实际选择内容。
- 部分操作的目标或处理意图。

### C. 左侧卡片详情

主要提供：

- 卡名和卡片类型。
- 完整效果文本。
- 等级、属性、攻守等辅助信息。
- 与卡牌数据库进行身份校验的证据。

三类信息需要独立识别，最后由 `EventFusion` 合并。

## 6.2 日志增量识别

日志区域会发生滚动和重复显示。不能简单地把每次 OCR 的全部结果追加到日志文件。

建议采用：

1. 将 OCR 文本分割为多行。
2. 规范化空格、标点及常见识别错误。
3. 计算当前文本与上一帧日志的重叠部分。
4. 找到最长匹配后缀和前缀。
5. 仅提取新增条目。
6. 为每条新增记录分配稳定的本地事件 ID。
7. 无法确认是否重复时，保存为待复核记录。

对于完全相同的重复动作，必须保留不同事件实例，不能仅通过文本去重。

## 6.3 事件分类

至少定义以下事件：

- `TURN_START`
- `PHASE_CHANGE`
- `CARD_REVEALED`
- `CARD_MOVED`
- `ACTIVATE_CARD`
- `ACTIVATE_EFFECT`
- `CHAIN_LINK_ADDED`
- `CHAIN_RESOLVED`
- `EFFECT_RESOLVED`
- `SUMMON_ATTEMPT`
- `SUMMON_SUCCESS`
- `CARD_ADDED_TO_HAND`
- `CARD_SENT_TO_GRAVE`
- `CARD_BANISHED`
- `CARD_SET`
- `CARD_DESTROYED`
- `LIFE_POINTS_CHANGED`
- `UNKNOWN_EVENT`
- `DUEL_FINISHED`

第一版不要求覆盖全部事件，但事件类型必须预先定义，并允许增加版本化的新类型。

## 6.4 事件融合

融合规则采用证据优先，而不是固定依赖某一种 OCR 结果。

例如：

- 日志显示某卡发动。
- 右上角效果框出现新文本。
- 左侧卡片详情与该卡匹配。

三项一致时，可以形成高置信度的效果发动事件。

如果日志显示效果处理，但右上角内容已经变化，不能立即认定新文本属于当前正在处理的效果，需要参考连锁顺序和时间戳。

事件冲突时：

1. 保存各来源的原始识别结果。
2. 生成候选事件。
3. 标记冲突原因。
4. 请求状态重建模块判断是否存在合理解释。
5. 无法解决时交给人工审核。

# 7. 对局状态模型

这是全项目最重要的公共数据结构。

不能把 OCR 文本直接传给 LLM 作为唯一输入。必须维护持续更新、可序列化、可验证的状态对象。

## 7.1 状态组成

```python
class DuelState:
    match_id: str
    state_version: int

    turn_number: int
    active_player: str
    phase: str

    players: dict

    visible_cards: list
    known_hidden_cards: list
    unknown_card_counts: dict

    chain: list
    pending_effects: list

    used_effects: list
    summon_restrictions: list

    legal_actions: list | None

    observation_confidence: float
    unresolved_events: list
```

这段代码表达数据结构意图，正式实现时应使用 Pydantic 模型，并为字段定义类型、默认值和验证规则。

## 7.2 必须区分三种状态

### Observation State

从玩家当前能够看到的画面中提取的信息。

### Reconstructed State

利用历史事件和规则约束，推断出的当前状态。

### Engine State

规则引擎中实际可执行的完整模拟状态。

三者不能混为一谈。

例如，公开回放中看不到对手手牌时，`Observation State` 必须保留未知信息。不能为了让模拟器运行，就把猜测出的卡片当作真实手牌。

## 7.3 状态版本管理

每次有效事件到达后递增 `state_version`。

所有路线搜索都记录其起始状态版本。

当出现新事件时：

- 如果事件没有改变当前计划的前置条件，可以继续执行已有规划。
- 如果事件改变了资源、限制或连锁状态，需要重新校验路线。
- 如果原路线已不成立，则取消过时搜索并触发重规划。

状态更新必须可回溯。人工修正某条日志后，系统应能够重新计算受影响的后续状态。

# 8. 卡牌知识库

## 8.1 目标

建立可供视觉识别、规则验证、Combo 搜索和本地模型共享的统一卡牌数据库。

建议至少包含：

- 稳定的卡牌标识。
- 日文、中文、英文卡名。
- 卡片别名。
- 卡片类型。
- 效果文本。
- 效果分段。
- 召唤条件和限制。
- 一回合一次等使用次数限制。
- 卡图文件或图像特征索引。
- 卡池和禁限表版本。
- 数据来源与许可信息。

## 8.2 数据来源

优先研究公开卡牌数据库、Project Ignis 相关资源和其他明确允许使用的数据源。

卡牌数据必须记录来源和版本。不得假定 EDOPro 的卡牌文本与 Master Duel 当前卡池、禁限表完全一致。

## 8.3 效果结构化

第一版以原始效果文本和卡牌身份为主。

后续逐步把效果拆解为：

- 发动条件。
- 发动代价。
- 发动时选择的对象。
- 结算操作。
- 效果限制。
- 每回合使用次数。
- 特殊召唤限制。

结构化结果必须保留原始文本，以便模型分析和人工审核。

# 9. 规则引擎与 Combo 搜索

## 9.1 规则引擎职责

ocgcore 负责提供模拟对局、合法操作和状态执行基础。

Combo Solver 负责搜索从给定起手或中间状态到目标终场的路线。

本项目不直接重写整个游戏王规则系统。

## 9.2 适配层

建立 `EngineAdapter`，至少支持：

- 初始化模拟对局。
- 设置已知的起手与初始场面。
- 执行合法操作。
- 查询当前合法动作。
- 查询关键资源与区域。
- 保存和恢复状态。
- 检查路线能否完整执行。
- 返回状态差异和错误信息。

如果现有 Solver 无法通过稳定 API 提供上述能力，则先通过命令行、回放和独立适配器集成，不要一开始就修改所有核心代码。

## 9.3 规则兼容性

EDOPro/ocgcore 与 Master Duel 的实际规则、卡池、卡片脚本版本可能存在差异。

因此所有验证结果必须带有规则引擎版本和卡池版本。

“模拟器中执行成功”只能说明路线在对应模拟环境中通过验证，不能直接等同于 Master Duel 中必然合法。

## 9.4 Combo 路线格式

每条路线应包含：

- 初始状态。
- 目标场面。
- 动作序列。
- 每步的前置条件。
- 每步的状态变化。
- 每步合法性验证结果。
- 路线完成状态。
- 资源消耗。
- 失败原因。
- 搜索预算和算法版本。

路线搜索应支持多个目标，例如：

- 最大化终场强度。
- 保留更多后续资源。
- 降低关键初动被打断的风险。
- 受到指定手坑后尽量恢复。
- 保证至少建立可接受的保底场面。

不同目标的评分函数必须独立配置。

# 10. 本地模型与策略分析

## 10.1 模型定位

本地 LLM 不应承担所有工作。

它负责：

- 理解当前局面。
- 解释卡片之间的交互。
- 对合法候选动作进行策略排序。
- 解释不同 Combo 的差异。
- 分析路线脆弱点。
- 对搜索器未覆盖的战术意图提出候选方案。

规则引擎负责合法性，Combo 搜索器负责验证路线，模型负责策略分析。

## 10.2 统一模型接口

定义 `ModelAdapter`，输入包括：

- 当前 Observation State。
- 当前 Reconstructed State。
- 已验证的合法动作。
- 可用卡牌知识。
- 当前目标。
- 搜索器提供的候选路线。
- 风险与不确定性信息。

输出采用结构化格式：

```json
{
  "recommended_action": {
    "action_id": "candidate_001"
  },
  "reasoning_summary": "先保护关键初动，避免过早消耗唯一检索资源。",
  "risk_level": "medium",
  "alternative_routes": [
    "route_002",
    "route_003"
  ],
  "uncertainties": [
    "对手隐藏手牌未知"
  ]
}
```

示例仅展示接口形式，不代表实际策略已经经过验证。

模型不得自由生成未经验证的动作并直接显示为确定可执行的操作。

## 10.3 训练路线

采用渐进式训练：

1. 卡牌知识与规则问答 SFT。
2. 已验证 Combo 轨迹 SFT。
3. 干扰与恢复路线训练。
4. 使用策略评价数据进行偏好优化。
5. 视数据质量和训练资源决定是否使用强化学习。

云服务器用于训练和批量数据生成，本地推理通过统一接口调用模型。

视觉系统、卡牌知识库、规则引擎和模型必须独立版本化，以便单独升级和回归测试。

# 11. 最终 UI 设计

最终界面不是一个普通聊天窗口，而是以游戏画面为中心的战术工作台。

建议采用 PySide6 主窗口，支持独立窗口、置顶分析面板和离线回放工作区。

## 11.1 主界面布局

```text
│                                           │ LP：8000 / 8000             │
│   卡片区域检测框                           ├────────────────────────────┤
│   当前效果区域                             │ 下一步推荐                  │
│   决斗日志区域                             │ ① 推荐操作                  │
│                                           │ ② 推荐理由                  │
│                                           │ ③ 操作风险                  │
├───────────────────────────────────────────┤                            │
│ 对局事件时间轴                             │ 备选路线                    │
│                                           │ A：最大终场                 │

```

该布局为设计目标，不要求第一版一次实现所有面板。

## 11.2 画面显示要求

用户需要能够：

- 查看原始游戏画面。
- 显示或隐藏识别框。
- 点击日志事件定位对应画面。
- 查看 OCR 原文和修正结果。
- 查看当前识别的卡牌与卡牌详情。
- 查看当前状态及未知信息。
- 手动修正错误事件。
- 重新执行受影响的状态重建。
- 查看模型推荐的动作和替代路线。

## 11.3 Combo 展示

Combo 不仅以自然语言展示，还要用可追踪的步骤列表：

```text
当前路线：A
状态：受到干扰，需要重新规划

✓ 步骤 1：初动效果成功
✓ 步骤 2：完成检索
✓ 步骤 3：特殊召唤
! 步骤 4：关键效果被无效
↻ 步骤 5：从当前状态重新规划

备选路线 B
- 继续使用剩余手牌
- 保留墓地资源
- 终场强度较低
- 规则验证：通过
```

所有路线步骤都应与 `state_version` 绑定，不能继续展示已经失效的旧路线为可执行建议。

## 11.4 数据审核界面

离线分析模式必须提供：

- 视频播放、暂停和时间定位。
- 当前帧截图。
- 决斗日志原始 OCR。
- 事件列表。
- 事件置信度。
- 卡牌身份候选。
- 状态重建结果。
- 手动确认和修正。
- JSONL 导出。

这将是第一阶段的核心用户界面，也将成为后续训练数据审核工具。

# 12. 数据结构与导出规范

## 12.1 事件记录

每条事件至少包含：

```json
{
  "schema_version": "1.0",
  "match_id": "match_000001",
  "event_id": "event_000042",
  "timestamp_ms": 125600,
  "turn": 2,
  "phase": "MAIN1",
  "event_type": "ACTIVATE_EFFECT",
  "actor": "PLAYER_A",
  "card_id": null,
  "card_name": "待确认",
  "effect_text": null,
  "confidence": 0.0,
  "status": "unresolved",
  "evidence": [],
  "state_version_before": 41,
  "state_version_after": 42
}
```

这是示例结构。正式实现应定义字段类型、枚举、必填项和向后兼容策略。

## 12.2 证据记录

证据至少应包含：

- 来源类型。
- 录像或采集时间戳。
- ROI 名称。
- OCR 原文。
- OCR 置信度。
- 图像路径或帧 ID。
- 人工修正记录。

原始图像应支持可配置保留策略。数据导出时不能只保存模型结论而丢失可追溯证据。

## 12.3 数据集分类

### Raw

原始录像、帧索引、OCR 原文和识别候选。

### Events

按时间排序的事件流。

### Reviewed

经过人工确认或高置信度规则校验的事件和状态。

### Training

经过数据质量过滤、脱敏与版本记录后用于训练的样本。

禁止将全部 OCR 输出直接混入训练集。

## 12.4 训练轨迹

一条 Combo 轨迹应关联：

- 初始状态。
- 观察信息。
- 动作序列。
- 中间状态。
- 干扰事件。
- 终场状态。
- 验证结果。
- 来源类型。
- 规则与卡池版本。

真实回放和模拟器生成数据必须标记不同的来源类型。

真实玩家执行过的路线不自动等于最优路线；模拟器搜索到的路线也不自动等于最佳策略。

# 13. 性能与可靠性目标

第一阶段先建立可测量的基准，再根据实测调整目标。

| 指标 | 初始目标 |
|---|---|
| 实时画面采集 | 目标 30 FPS |
| OCR | 只处理发生变化的 ROI |
| 日志新增检测 | 事件发生后 500–1000 ms 内更新为初步目标 |
| 状态更新 | 新事件到达后立即调度 |
| 模型推理 | 异步执行，不阻塞画面采集 |
| 搜索器 | 可取消过期任务，支持预算限制 |
| 队列 | 有界队列，避免延迟持续累积 |
| 数据导出 | 结构化、可追溯、可恢复 |
| 错误处理 | 单模块异常不导致整个 UI 崩溃 |

以上时间为待验证的工程目标，不是已测得的性能承诺。

## 13.1 延迟控制

采集线程、OCR 线程、事件融合、状态重建、路线搜索和模型推理应异步运行。

关键原则：

- OCR 不能阻塞帧采集。
- 模型不能阻塞事件处理。
- 搜索不能阻塞 UI。
- 新状态到达后，旧搜索结果必须经过状态版本检查。
- 长时间没有得到可靠结论时，应明确显示“分析中”或“状态不确定”。

## 13.2 置信度与安全降级

低置信度时，不应继续假定路线成立。

例如：

- 卡名不确定：保留候选。
- 连锁未结算：暂停推进路线。
- 效果结果无法确认：标记待确认。
- 状态与规则引擎矛盾：停止输出确定性路线。
- 搜索超时：显示当前最佳已验证路线和搜索状态。

# 14. 分阶段实施计划

## Phase 0：工程基础

目标：建立可运行的项目骨架。

交付：

- Python 项目结构。
- 配置加载。
- 日志系统。
- PySide6 主窗口。
- pytest 基础测试。
- Git 版本管理。
- 依赖锁定。
- 统一帧、事件和状态数据结构。

验收：项目可以启动，窗口正常显示，测试通过。

## Phase 1：实时采集与离线录像共用管线

目标：实现稳定帧输入。

交付：

- 游戏窗口定位。
- 实时画面采集。
- 录像文件读取。
- ROI 可视化和手动校准。
- 帧时间戳。
- 有界队列。
- 原始帧调试工具。

验收：同一 ROI 识别代码能够处理实时帧和录像帧。

## Phase 2：决斗日志与当前效果识别

目标：从画面提取可见事件。

交付：

- 决斗日志 OCR。
- 当前效果框 OCR。
- 左侧卡片详情 OCR。
- 日志增量拼接。
- 卡名模糊匹配。
- 原始 OCR 结果保存。
- 置信度与人工复核标记。

验收：能够从一段录像导出按时间排序的日志事件，且可以追溯到原始画面。

## Phase 3：事件融合与状态重建

目标：将 OCR 结果转为统一事件流和可观察状态。

交付：

- 事件分类。
- 多来源证据融合。
- 回合和阶段跟踪。
- 连锁和效果事件建模。
- 卡牌区域变化跟踪。
- 状态版本管理。
- 不确定状态处理。
- 人工修正和回放重算。

验收：能够展示一场对局的事件时间轴，且每条事件都能定位到证据。

## Phase 4：卡牌知识库与规则验证

目标：建立统一卡牌数据与验证接口。

交付：

- 卡牌数据库导入。
- 卡名别名索引。
- 卡图匹配。
- ocgcore 适配层。
- 状态验证接口。
- 规则和卡池版本记录。
- 差异诊断。

验收：对选定的测试卡组，能够验证一批人工确认的动作轨迹，并记录不兼容或无法复现的原因。

## Phase 5：Combo 搜索与动态重规划

目标：能够分析路线并在受到干扰后重新规划。

交付：

- Combo Solver 适配。
- 指定起手和目标。
- 多路线搜索。
- 资源消耗统计。
- 干扰测试。
- 过期路线检测。
- 状态版本绑定。
- 备选路线 UI。

验收：使用可复现的测试状态，验证路线成功、路线失效、状态变化和重新规划四类场景。

## Phase 6：本地模型与训练数据生成

目标：让模型能够解释局面并对候选路线排序。

交付：

- 统一模型接口。
- 卡牌知识 SFT 数据。
- 已验证 Combo 轨迹。
- 干扰与恢复样本。
- 数据质量过滤。
- 训练、验证、测试数据隔离。
- 模型评测报告。
- 路线解释与风险提示。

验收：模型能够基于给定状态输出结构化建议，且推荐动作能够映射到合法候选集合。

## Phase 7：实时战术助手

目标：将前面各模块集成到实时分析界面。

交付：

- 实时状态面板。
- 下一步推荐。
- Combo 进度。
- 干扰风险提示。
- 动态重规划。
- 识别证据面板。
- 低置信度提示。
- 完整的离线复盘功能。

验收：实时画面变化能够驱动状态更新，旧路线会在失效时停止显示为有效建议，系统能够持续运行并记录异常。

# 15. 第一版验收测试

项目不能只以“界面能打开”为完成标准。

必须建立固定测试素材和可重复的测试流程。

## 15.1 视觉测试

- 不同窗口尺寸。
- 不同分辨率。
- 决斗日志滚动。
- 卡片详情切换。
- 效果文本变化。
- 动画遮挡。
- 窗口失焦和重新获得焦点。
- 录像暂停与跳转。

## 15.2 事件测试

- 同一日志行连续出现。
- 相同卡牌连续发动效果。
- 连锁开始与结束。
- 多选一效果。
- 日志和效果框不同步。
- OCR 卡名错误。
- 事件顺序无法确定。

## 15.3 状态测试

- 卡片加入手牌。
- 卡片送入墓地。
- 卡片除外。
- 特殊召唤。
- 效果被无效。
- 一回合一次效果已使用。
- 连锁尚未结算。
- 隐藏信息不足。

## 15.4 搜索测试

- 正常 Combo 成功。
- 指定手坑打断。
- 初动被无效。
- 资源消耗发生变化。
- 原路线失效。
- 重新搜索成功。
- 搜索超时。
- 新状态到达后取消旧搜索。

## 15.5 数据测试

- JSONL 每行均为有效 JSON。
- 事件 ID 不重复。
- 时间戳可排序。
- 状态版本连续且可追溯。
- 原始证据存在。
- 未确认的事件不会被误标为高置信度。
- 同一对局的派生样本不会泄漏到训练集和测试集两边。

# 16. 开发规范

## 16.1 模块接口优先

每个模块应先定义输入、输出、错误类型和测试，再开始复杂实现。

不允许将 OCR、状态更新、搜索和模型调用全部堆积在单个主循环中。

## 16.2 配置驱动

ROI、采集频率、OCR 阈值、模型后端和搜索预算都必须通过配置控制，不应散落在源码中。

## 16.3 可观察性

必须记录：

- 帧采集时间。
- OCR 耗时。
- 事件融合耗时。
- 状态重建耗时。
- 搜索耗时。
- 模型推理耗时。
- 识别失败原因。
- 队列长度。
- 被取消的过期任务数量。

## 16.4 版本化

以下内容需要独立记录版本：

- 事件 Schema。
- 状态 Schema。
- 卡牌数据库。
- 规则引擎。
- 搜索器。
- 模型权重。
- 训练数据集。

## 16.5 使用与合规边界

第一阶段采用用户提供的录像、手动操作的公开回放和可合法获取的数据开展开发。

实时模式优先限于画面采集和只读分析。不要把未经授权的进程注入、私有协议拦截或自动对局操作作为系统依赖。正式接入 Master Duel 前，需要单独评估游戏条款及相关许可。

# 17. 开始实施时的任务顺序

开发 Agent 不应一次实现整个项目，而应严格按照下面的顺序提交可验证结果。

1. 初始化目录、依赖和测试框架。
2. 定义 `Frame`、`DuelEvent`、`DuelState` 的 Schema。
3. 实现实时窗口采集和录像文件采集两个后端。
4. 实现 ROI 配置和可视化校准。
5. 实现日志区域 OCR，并保存原始识别结果。
6. 实现日志增量跟踪和去重测试。
7. 实现当前效果框和卡片详情识别。
8. 实现事件时间轴 UI。
9. 实现 JSONL 导出和人工审核。
10. 建立固定录像测试集和识别质量报告。
11. 再实现状态重建和卡牌知识库。
12. 最后接入规则引擎、Combo Solver 和本地模型。

每一步都必须提交可运行代码、测试结果和已知限制。不要在底层采集尚未稳定时就开始开发复杂 Combo 推理。

# 18. 第一版完成标准

第一版不是一个完整的游戏王 AI，而是一个可以持续扩展的工程基础。

必须完成：

- 能实时读取游戏窗口。
- 能分析离线录像。
- 能校准并预览多个 ROI。
- 能识别决斗日志和当前效果描述。
- 能增量提取日志事件。
- 能将事件按时间排列。
- 能查看事件对应的原始证据。
- 能人工修正识别结果。
- 能导出 JSONL。
- 能在实时模式和录像模式间复用同一套处理代码。
- 具备后续接入卡牌数据库、规则引擎、Combo 搜索和本地模型的稳定接口。

第一版完成后，再逐步把事件流转换为可验证的完整对局状态，进而实现 Combo 推演、抗干扰路线搜索和实时战术推荐。

**最终设计原则：画面负责提供证据，事件层负责描述发生了什么，状态层负责维护当前局面，规则引擎负责验证合法性，搜索器负责寻找路线，本地模型负责分析策略。**

整个系统围绕这六个职责构建，避免让任何一个模型独自承担所有任务。
